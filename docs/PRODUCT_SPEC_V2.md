# 下一版产品规格：四地比较与串联行程

## 1. 本版目标

在不向首页增加新模块的前提下，增加冉庄地道战纪念馆详情，并把四个目的地从彼此独立的介绍页连接成一个可比较、可组合、可安排行程的静态规划工具。首页既有页眉、河北地图、摘要和导航必须同步四地数据。

本版解决三个连续问题：

1. 四地各自什么时候开放，哪一天可能无法参观；
2. 选中的几个地点在主题、用时、强度、交通和准备上有什么差异；
3. 怎样把所选地点按合理顺序排进一天或多天，并处理通勤、午餐和住宿。

## 2. 页面与入口

- `/`：保持当前河北地图、摘要和交互结构，地图与页眉同步显示四个目的地；不恢复首页比较区，也不新增规划模块。
- `/destination/:destinationId`：继续使用共用详情模板；四个详情页均增加开放时间模块和“加入对比与行程”入口。
- `/destination/ranzhuang-tunnel`：新增冉庄地道战纪念馆详情页。
- `/planner`：新增四地比较与串联行程页。详情页入口通过 URL 参数预选当前目的地，例如 `/planner?places=xibaipo`。

`destinations` 是四地唯一完整数据源。首页、页眉、详情页和规划页均从四地数据派生；不得通过单独三地列表把冉庄排除在既有组件之外。

## 3. 四地勾选与简要比较

页面顶部显示四个紧凑的选择项，使用真实复选框。选择后比较内容立即更新，不需要提交表单。

比较字段限定为游客决策所需的高信号信息：

- 主题与空间类型；
- 日常开放时段、停止入场与常规闭馆日；
- 建议游览用时与强度；
- 公共交通可行性、自驾适配度与主要出发枢纽；
- 预约或证件要求；
- 午餐便利程度与适合的住宿落点；
- 最适合的游客和关键限制。

桌面端按目的地分列；移动端按目的地纵向排列，并保留顶部已选地点摘要。比较信息必须同时出现，不能退化成一次只查看一个地点的轮播。

状态规则：

- 0 个：显示四地选择和简短引导；
- 1 个：显示该地摘要，可继续勾选，但不生成串联路线；
- 2 至 4 个：显示比较和路线规划；
- 取消选择后，比较列、路线和总计同步更新；
- 选择状态、交通方式、日期和天数写入 URL 查询参数，刷新和分享后可恢复。

## 4. 开放时间模型

开放时间不能继续只存在于自由文本 `advisory` 中。每个目的地新增结构化字段：

```ts
interface OpeningSchedule {
  regularDays: string
  openTime: string
  closeTime: string
  lastEntryTime?: string
  closedDays: string[]
  reservation?: string
  exceptions: string
  sourceLabel: string
  sourceUrl: string
  verifiedAt: string
}
```

页面显示“日常规则”和“出发前核验”两层信息。规划器可以依据日期判断星期几，但法定节假日、临时闭馆和天气管制只给出警告及官方链接，不宣称自动掌握实时变化。

## 5. 串联路线输入

路线区至少提供：

- 已选目的地：2 至 4 个；
- 出发日期：用于检查星期与常规闭馆日；
- 交通偏好：自驾、公共交通；
- 可用天数：自动、1 天、2 天、3 天；
- 行程节奏：轻松、标准、紧凑；
- 出发落点：石家庄市区、保定市区或首个景点附近；只展示经过研究确认可支持的选项。

不要求定位权限，不调用需要公开密钥的实时路线 API，不提供购票或酒店预订。

## 6. 路线生成规则

四地之间建立可核验的交通关系数据，而不是只画直线：

```ts
interface ConnectionEdge {
  from: DestinationId
  to: DestinationId
  mode: 'car' | 'public-transit'
  durationMinutes: [number, number]
  distanceKm?: [number, number]
  via: string[]
  constraints: string[]
  sourceLabel: string
  sourceUrl: string
  verifiedAt: string
}
```

最多只有四个目的地，前端可枚举所选地点的访问顺序，按以下优先级筛选：

1. 排除与常规闭馆日明确冲突的安排；
2. 避免抵达时间晚于停止入场时间；
3. 优先减少通勤时间和跨城市往返；
4. 控制每日总时长，并按强度给山地行程留出更大缓冲；
5. 公共交通资料不足的路段不得生成看似确定的班次，改为明确提示需要二次核验或更换交通方式。

输出一个推荐顺序，并在存在明显取舍时给出一个备选方案，例如“通勤更短”和“体力更轻松”。所有耗时使用范围和缓冲，不给出虚假精确到分钟的承诺。

## 7. 日程输出

结果按“第 1 天、第 2 天……”组织，每天包含：

- 当日出发地和建议出发时间段；
- 每段交通方式、预计耗时范围、途经关系和核验入口；
- 每个目的地的预计抵达、参观时段、停止入场风险和离开时间；
- 11:30 至 13:30 附近的午餐窗口，以及适合用餐的区域类型；
- 当日体力、预约、证件、天气、饮水和返程准备；
- 当天结束后的住宿落点及理由；
- 当日参观、通勤、缓冲和总时长汇总。

午餐默认推荐“景区服务区、县城或城市交通枢纽附近”等区域策略。没有可靠来源和稳定营业信息时，不推荐具体餐厅。住宿默认推荐石家庄市区、保定市区、易县城区等落脚区域及其交通意义，不虚构具体酒店。

## 8. 视觉与交互

- 规划页是高频工具界面，使用紧凑选择栏、对比表和按天时间轴，不制作营销式 Hero。
- 四个地点使用稳定的颜色和编号，但选择状态同时通过复选框、描边和文字表达。
- 地图展示真实地理位置与公路/交通关系；选中地点和当前日程分段联动高亮。
- 点击比较列中的地点可进入详情；从详情返回规划页时保留已选项。
- 重新生成、切换交通方式、增加天数和删除地点均提供明显反馈，且不造成布局跳动。
- 手机端不强行压缩四列表格，改为纵向地点摘要与按天时间轴。

## 9. 数据与来源边界

- 冉庄的开放、预约、内部景点、导览、交通和图片必须先完成来源研究。
- 四地开放时间统一重新核验，不能沿用模糊或已冲突的旧文案作为结构化事实。
- 六组地点对之间的自驾关系均需来源；公共交通只对能可靠核验的路段建模。
- 图片仍遵守 `CONSTRAINTS.md`：正式图片必须有使用依据，否则使用统一占位图。
- 路线建议必须标明生成依据、核验日期和“出发前再次确认”的入口。

## 10. 验收场景

- 勾选任意 1、2、3、4 个地点时，比较区域内容正确且无残留列。
- 任意 2 至 4 个地点可生成计划；所有组合均不会崩溃或引用未选地点。
- 选择常规闭馆日时能看到明确冲突，系统不会照常生成不可执行参观段。
- 自驾与公共交通切换后，路线、耗时、准备和风险提示同步变化。
- 一日无法合理容纳时，系统明确建议增加天数，不通过压缩参观时间制造“可行”。
- 每天都有交通、参观、午餐、缓冲、住宿/返程和准备信息。
- 四个详情页均显示结构化开放时间及具体来源。
- 首页不新增内容模块，原有地图、摘要和交互方式保持一致；点位、页眉及相关文字正确扩展为四地。
- 在 1440×900、768×1024、390×844 下无横向页面溢出、遮挡或不可触控操作。
